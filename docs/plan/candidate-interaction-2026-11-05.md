# 候选摆放、整词浏览上限与补全机制评估

## 本轮范围

用户确认问题是“翻很多页也找不到生僻词，希望早点按单字选”，不是候选计算卡顿。后续实现已加入 Windows 浮动候选窗的上方反序、普通整词额度与单字/完整列表菜单，以及发布前的离线体验门禁。默认额度经 9/18/27 对比选择 27；测量与覆盖范围见 [实施记录](../notes/typing-experience-2026-11-05.md)。代码补全式续写仅保留下面的调研，不实现。Actions 使用约束已写入 CLAUDE.md，常规开发本地验证，最终安装包才手动触发。

## 让首选靠近输入行

用户目标是距离关系：窗口在文字上方时，候选 1 紧靠输入行；在文字下方时仍正常排列。当前术语“横排/竖排”与上下方向要分开：竖排是一行一个候选，横排单行没有上下候选顺序，横排矩阵有多行。

竖排方案示意（数字仍对应原来的逻辑候选）：

```text
窗口在上方             窗口在下方
  9 第九项               正在输入的文字｜
  …                      1 首选
  2 第二项               2 第二项
  1 首选                 …
正在输入的文字｜         9 第九项
```

| 布局 | 窗口在文字上方 | 窗口在文字下方 |
| --- | --- | --- |
| 竖排 | 视觉自上至下 9…1，1 在底部 | 视觉自上至下 1…9 |
| 横排单行 | 保持左至右 1…9，不倒置文字；候选条靠近输入行，译文等辅助区放远侧 | 保持左至右 1…9 |
| 横排矩阵 | 第一组候选整行放底部，后续组向上展开；每行仍左至右 | 第一组整行放顶部，后续组向下展开 |

不能反转 Core 返回的候选数组：那会改变空格首选、数字键、模型排序和学习记录。建议只增加展示方向，逻辑索引仍为 0…n。竖排视觉行映射 `n - 1 - i`；矩阵只反转行号，列号不变。鼠标区域的 `HitTarget::Candidate(i)` 和译词的候选索引都保留逻辑 i。文字本身、译文字符和主题装饰不镜像。

当前 `apps/windows/server/src/ui/candidates/mod.rs::show` 先渲染、量内容高度，再由 `place` 优先放光标下方，放不下改上方。共享渲染 `Frame` 只有候选和矩阵列数，没有实际上下位置。实现需要先确定可用空间、量尺寸、确定方向，再对候选区域布置；方向变化加入渲染缓存身份。普通帧保持不变时复用量测，避免每个按键都额外完整绘制两次。方向切换以实际内容区和输入行是否分离判定，多屏负坐标、阴影、屏幕内夹取都需处理；处于重叠/侧边回退时不能盲目认定为“上方”。

普通自绘窗口、Windows GDI 回退、TSF 搜索宿主内窗口是三条显示路径；系统自己绘制的 TSF 候选无法承诺由我们控制顺序。第一版应清晰标明覆盖范围，不能只改一个主题就声称全部支持。共享渲染器的布局信息也应由 macOS 壳提供，Core 不掺入窗口坐标。

方向键应另明确规则：建议竖排 ↑/↓ 按屏幕相邻项移动，上方显示时 ↑ 从候选 1 到候选 2，数字/空格和翻页语义保持一致；矩阵 ↑/↓ 同样按视觉行映射。这要求把展示方向传给导航适配，不能仅靠渲染反转。方向在一轮输入中尽量稳定，用户导航时不让晚到的结果重排。

验收应覆盖 1/2/9 项、上下切换、空格与 1…9、点击和右键、译词点击、箭头、翻页、矩阵空位、100/150/200% DPI、多屏边缘及不同主题。先做本地布局/命中测试和离屏图片，再集中一次最终 Windows 构建；真实输入框操作仍需 Windows 验证。

## 限制整词浏览，让单字更早出现

当前有四种不同上限，不能混为一谈：

| 层 | 当前机制 | 对问题的影响 |
| --- | --- | --- |
| 每页展示 | 1–9 项，可配置 | 只改页大小不能减少翻页总量 |
| 本地总候选 | `MAX_CANDIDATES = 500` | 仍可形成几十页；含整词和单字，直接全局缩小会裁掉生僻单字 |
| 候选分类 | `WORDS_BEFORE_SINGLE_CHARS = 6`、补全前置最多 3 条；最终保证首个单字不太靠后 | 已部分照顾拆字，但只保证首个单字的位置，不等于所有常用拆字候选都好找 |
| 搜索与模型 | 整句显示最多 3 条；Viterbi 每格 6、简拼格 20、束宽 8；知意比较内部可保留 16 条整句 | 这些主要约束计算和准确度，不宜为缩短列表一起砍掉 |

建议区分“完整拼音精确整词”“猜测/扩展词”“只覆盖开头的词”“首音节单字”。先去重，再为普通浏览设词语额度，单字走独立名额；内部搜索规模与界面浏览额度分开。

起始试验值为 18 条；实际对比后选用 27 条：普通整词最多 27 条，其中超出输入的猜测补全最多 3 条；首屏/下一屏中给首音节单字明确入口，继续选完第一个字后自动沿用剩余拼音。单字列表保留更多项，避免生僻字本身失去可达性。`m → 吗` 等已学习首选和置顶结果应优先占位；若学习记录超过额度，也需有稳定上限和“更多候选”入口，不能名义限额却无限豁免。

已对比 9/18/27 条整词：修正单字视图排序后，三种额度均通过门槛；9 条的总操作数仍高于完整列表，18 条有一条简拼需要更多拆字，27 条保留这条整词、操作最少且首选/前五不退步。50 条样本不足以证明对所有人最优，后续继续扩展冻结样本。小页模式下不承诺固定“两页内见全部单字”；应保证单字入口的位置，而非只按总数计算页数。

“按单字选”建议只改变当前输入的候选视图，不删输入、不启用/关闭词库、不生成新拼音。可先复用现有拼音光标圈定首音节机制，确认 Windows 展示是否易发现；再评估一个可配置的显式入口。`Tab` 已可能用于翻页，不能直接抢作新功能。生僻名字不能简单按低词频过滤，否则仍会误删用户真正需要的词。

更重要的保护：当前用户已翻页/移动高亮时，候选应稳定；主动展开“更多候选”后才放宽展示限额。普通浏览的末页不应自动排出无穷猜测，已选择的单字和剩余拼音仍按原来的上屏、学习、撤销规则处理。

## 类似代码补全的机制能否使用

结论：值得借鉴交互与请求生命周期，先试本地前缀偏好和少量短语建议；跨应用通用灰字和自动改写不是第一阶段目标。

### 可以直接借鉴的部分

VS Code 的 `recentlyUsedByPrefix` 会记住某个前缀选中过的补全项，例如 `co → console`。这与用户期望的 `m → 吗` 很接近。青简已有按输入串累计选择的表，刚修复模型覆盖学习首选；可进一步比较“累计频率”“最近一次”“频率加近期性”三种策略，不能把长期习惯与临时误选等同。应包括撤销、删除重打、简拼/全拼、不同应用和私密输入的测试。[IntelliSense 官方说明](https://code.visualstudio.com/docs/editing/intellisense)

VS Code 内联补全接口区分自动触发和用户显式触发，提供文档、位置、上下文及取消令牌；自动场景可以只给一个建议。对应输入法可采用“本地候选立即返回；停顿后最多显示一条短续写；继续输入、切会话、上屏、进入私密状态就作废”。青简已有组句历史、应用前文、异步 worker 和序号过滤，可复用；已开始的模型前向不能假设能硬中断。[InlineCompletionItemProvider](https://code.visualstudio.com/api/references/vscode-api#InlineCompletionItemProvider)

代码补全支持明确接受、拒绝和分段接受。输入法可先在候选窗单独区域显示预测后缀，只有显式操作才插入，普通空格继续正常选词；逐词接受比一次生成长段落更便于纠正。具体键位需遵守现有映射，不直接照搬 Tab。[VS Code 内联建议](https://code.visualstudio.com/docs/editing/ai-powered-suggestions)

### 第一阶段适合做的原型

| 原型 | 示例 | 数据与代价 | 建议 |
| --- | --- | --- | --- |
| 前缀偏好 | `m` 常选「吗」后优先显示 | 现有选择表，不加常驻模型 | 优先，与学习修复衔接 |
| 本地短语补尾 | 已输入「麻烦确认」后提示「一下时间」 | 本地词库/用户自愿学习的短语或 n-gram，少量有界查找 | 优先小范围试验，低置信度不显示 |
| 当前会话词复用 | 本段已正确选过某个名字，后续相同拼音优先 | 有界会话缓存，失焦/新文档应处理作用域 | 值得试验，避免跨应用名字误提升 |
| 云端/本地模型续写 | 「我明天下午」提示短后缀 | 网络或推理 CPU/内存；仅用户启用后运行 | 后续可选，最多一条、可取消、无结果直接继续输入 |
| 编辑器式下一处修改 | 自动建议替换正文其他位置 | 需要可靠文档版本、编辑范围与撤销事务 | 暂缓；输入法不具备通用编辑器语义 |

模型建议必须区分“当前拼音转换”和“尚未输入的后缀”。前者受已输入读音约束，后者清楚标为续写；不能把无拼音后缀混成普通首选，误按空格就整段发送。个人短语库要有条数/字节上限，低频学习不得每键扫描全部历史。

### 灰字为什么需要宿主支持评估

编辑器掌握文档版本、显示装饰层、替换范围和撤销栈，输入法只有宿主愿意暴露的 TSF 文本范围。`ITfRange::GetText` 需要有效读锁，`RequestEditSession` 的同步请求并不保证成功；代码中虽然已有 `edit/surrounding.rs` 读取前文，但这不等于所有应用都提供足够上下文。[GetText](https://learn.microsoft.com/en-us/windows/win32/api/msctf/nf-msctf-itfrange-gettext)、[RequestEditSession](https://learn.microsoft.com/en-us/windows/win32/api/msctf/nf-msctf-itfcontext-requesteditsession)

把预测文字临时写进正文再标灰，可能被应用当成真实内容，影响发送、复制、撤销和无障碍读取；自行悬浮灰字又要处理多行、滚动、DPI、字体与焦点。第一阶段使用已有候选窗预览后缀更可控。若日后要精确的编辑器灰字，应评估编辑器插件适配；不承诺通用 TSF 注入能达到同样效果。

### 评价方式与执行顺序

评价按减少的真实敲键、建议接受率、误接受/撤销率、候选位置稳定性、P95 延迟、停键推理次数及增量 RSS；不能仅统计“模型生成了多少字”。测试语料应含姓名、聊天短语、办公短句、英文/代码、已有后文与密码输入，不把标准答案灌进学习库。

建议顺序：先限制整词普通浏览并提供单字入口；再实现上下方向相关的展示映射与本地命中验证；最后只做轻量补全原型。每一步本地验证，集中最终安装包才运行一次 Windows Actions；出现可本地发现的问题先修好，不用多轮云构建替代本地分析。
